AUDITORIA — CONSTRUCTOR WEB (LANDING)
BiowebLink
Fecha: 2026-10-24
Alcance: solo lectura sobre el codigo del constructor web. No se ejecutaron migraciones ni pruebas contra Supabase.

======================================================================
1. RESUMEN
======================================================================

El Constructor Web es un editor de landing pages basado en formularios y vista previa embebida. No es un editor visual drag & drop.

Funciona sobre una unica plantilla visual llamada "creative", pensada para tatuadores, fotografos, artistas y disenadores. No existe una plantilla ni un preset de contenido para abogados.

El profesional edita secciones, tema, logo, slug, visibilidad de secciones y SEO. Al guardar, la landing se publica directamente: no hay un flujo de borrador/publicacion separado en la interfaz.

La escritura se realiza exclusivamente mediante la Edge Function admin-manage-landing, que usa service_role y obtiene el business_id desde el JWT. La lectura publica se hace por slug y solo para landings publicadas.

Fortalezas:
- Secciones suficientes para una web de servicios.
- Tema visual muy configurable.
- Vista previa fiel a la landing real.
- Escritura centralizada y con control de negocio.
- Subida y compresion de imagenes.

Limitaciones principales:
- Una sola plantilla y sin selector de plantilla.
- Sin editor visual drag & drop.
- Sin borradores ni historial de versiones.
- Sin IA integrada en el constructor.
- SEO generado en el cliente, sin SSR.
- Esquema de landing_pages sin CREATE TABLE versionado.
- Slug editable sin validacion de unicidad.
- No hay contenido especifico para estudios juridicos.

3. ARQUITECTURA Y FLUJO
======================================================================

Stack:
- Vite + React + TypeScript.
- react-router-dom.
- Tailwind + Radix UI.
- Supabase Postgres, Storage y Edge Functions.

Flujo de edicion:
1. El admin entra a /admin.
2. Abre Presencia Web > Constructor de sitio web.
3. LandingAdmin carga la landing con admin-manage-landing, action "get".
4. El editor modifica estado local: secciones, tema, slug, logo y visible_sections.
5. Al guardar, useLandingCrud invoca admin-manage-landing con action "publish".
6. La Edge Function deriva business_id del JWT.
7. Verifica negocio activo, trial vigente y modulo landing.
8. Crea o actualiza la fila de landing_pages.
9. Marca status como "published".
10. El publico lee la landing por slug con status "published".

No hay escrituras directas a landing_pages desde el frontend.
La unica lectura publica directa esta en useLandingData.ts.

======================================================================
5. PERSISTENCIA Y SEGURIDAD
======================================================================

Edge Function: admin-manage-landing.

Acciones:
- get: devuelve la landing del negocio, incluidos borradores.
- save: crea o actualiza sin publicar.
- publish: crea o actualiza y marca como publicada.
- Cualquier otra accion devuelve error.

Campos persistidos:
- sections
- theme
- template
- visible_sections
- logo_url
- slug
- updated_at

No persiste:
- seo (columna legacy)
- El SEO real se guarda dentro de sections.seo_marketing.

Seguridad:
- authenticateToken valida el JWT y relee admin_users.
- business_id nunca se acepta desde el cliente.
- checkBusinessAccess valida negocio activo, trial, plan y modulo landing.
- La busqueda de la landing existente se hace por business_id.
- El update incluye business_id como segunda condicion.
- No se puede escribir sobre la landing de otro negocio usando un id arbitrario.

RLS:
- Lectura publica solo de landings publicadas.
- service_role administra la escritura.
- La policy historica que permitia insert/update/delete anonimo fue cerrada.
- La migracion 20261012010000 garantiza RLS y policies canonicas si las tablas existen.

Deriva de esquema:
- No existe CREATE TABLE landing_pages en el repositorio.
- No se puede reconstruir la tabla desde cero solo con las migraciones.
- El esquema real solo se puede confirmar contra Supabase.

Observacion:
- La migracion 20260721000000 define template DEFAULT 'minimal'.
- El codigo solo conoce 'creative'.
- La Edge Function fuerza 'creative' al crear, pero el default de la base queda inconsistente.

======================================================================
6. VISTA PREVIA
======================================================================

La vista previa usa el mismo componente que la pagina publica:
- PreviewPanel renderiza LandingPage.
- Pasa initialData con el estado actual del editor.
- isPreview ajusta comportamientos propios del contenedor.
- Header y Hero tienen un caso especial para no desbordar la vista previa.
- Las secciones ocultas no se renderizan.
- Los cambios se ven sin guardar.

Ventaja:
- Alta fidelidad entre editor y publicacion.

Limite:
- No permite arrastrar, mover ni editar directamente sobre la vista previa.
- No hay zoom, device preview ni inspeccion de componentes.

7. PLANTILLAS Y DISENO
======================================================================

Plantilla:
- LandingTemplate = 'creative'.
- TEMPLATES contiene solo "Creativa".
- La descripcion comercial menciona tatuadores, fotografos, artistas y disenadores.
- No hay plantilla "lawyer", "legal", "corporate" ni similar.

TEMPLATE_STYLES:
- cardRadius
- sectionSpacing
- headerStyle
- heroLayout
- cardShadow
- buttonRadius

Uso real:
- headerStyle se usa en Header.
- cardRadius, sectionSpacing, cardShadow y buttonRadius se usan en secciones.
- heroLayout esta definido pero no se encontro uso.

Acoplamiento:
- Varios componentes tipan ts como typeof TEMPLATE_STYLES['creative'].
- Agregar una plantilla nueva exige mantener la misma forma y revisar esos tipos.

Hero:
- HeroTemplate = 'centered' | 'image' | 'video'.
- Etiquetas: Centrada, Con Imagen, Con Video.
- HeroSelector y HeroForm permiten cambiar la variante.
- Existe migracion de datos viejos de Hero.

Tema:
- Mas de 100 claves.
- Colores por seccion.
- Tipografias, tamanos, pesos y estilos.
- Fondos, separadores y botones.
- 13 tipografias disponibles desde Google Fonts.
- Parallax configurable.
- Separadores entre Hero/About y CTA/Footer.
- El parallax se desactiva si hay separadores activos.

Para abogados:
- La plantilla actual puede usarse, pero no transmite el codigo visual esperado.
- Falta una variante sobria, institucional y editorial.
- Agregar una plantilla requiere ampliar el tipo, agregar estilos, agregar selector y revisar tipos acoplados.

======================================================================
9. LECTURA PUBLICA
======================================================================

Hook: useLandingData.

Consulta:
- landing_pages por slug.
- status = published.
- usa anon key.
- limita a una fila con maybeSingle.

Ademas:
- Configura BusinessContext.
- Carga theme y sections.
- Calcula TEMPLATE_STYLES.
- Carga Google Fonts.
- Aplica fuente, colores y estilos globales.
- Respeta visible_sections.
- Verifica acceso al modulo landing.

Si el plan no incluye landing:
- Se muestra ModuleBlockedScreen.

Si no existe la landing o no esta publicada:
- La pagina no muestra el sitio.

Riesgo:
- Si hay slugs duplicados, maybeSingle puede devolver error.
- No se confirmo una constraint UNIQUE para landing_pages.slug.

======================================================================
10. SEO
======================================================================

El SEO efectivo vive en sections.seo_marketing.

LandingPage aplica en el cliente:
- title
- meta description
- canonical
- Open Graph
- Twitter Card
- verificacion de buscadores
- pixels y scripts de marketing

La columna seo existe en el tipo LandingPage, pero:
- admin-manage-landing no la guarda.
- El editor no la edita directamente.
- Parece una representacion legacy.

Riesgos:
- No hay SSR ni prerender.
- Los metadatos dependen de JavaScript.
- Los crawlers que no ejecutan JavaScript pueden no ver el SEO final.
- No hay schema.org LegalService/Attorney.
- No hay generateStaticParams ni sitemap especifico por landing.
- El slug editable sin unicidad puede afectar canonicas y URLs.

======================================================================
12. HALLAZGOS Y RIESGOS
======================================================================

Alta prioridad:
1. No hay CREATE TABLE versionado de landing_pages.
2. El default template = 'minimal' no coincide con el unico template del codigo.
3. El slug se puede editar sin validacion de unicidad.
4. El guardado publica siempre; no hay borrador real en la UI.
5. No hay plantilla ni contenido para abogados.
6. El SEO es client-side.
7. No hay tests visibles del constructor.

Media prioridad:
8. TEMPLATES y setTemplate son codigo muerto en la practica.
9. heroLayout no se usa.
10. La columna seo y sections.seo_marketing se superponen.
11. No hay historial de versiones ni rollback.
12. No hay preview por dispositivo.
13. No hay validacion de schema de sections antes de guardar.
14. No hay control de slugs reservados.

Baja prioridad:
15. Los tipos estan acoplados a TEMPLATE_STYLES['creative'].
16. No hay biblioteca de contenido reutilizable.
17. No hay indicador de cambios sin guardar.
18. No hay autosave.
